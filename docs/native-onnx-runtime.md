# Native ONNX Runtime in release builds

ChampionVibe uses ONNX Runtime **1.24.3** for native model validation and stem separation. `ort` rc.12 requests API 24. Kokoro speech still uses a separate WebAssembly runtime in the WebView.

- **Windows x64:** `scripts/stage-onnx-runtime.py windows` verifies the SHA-256 of Microsoft’s [ONNX Runtime DirectML 1.24.3 distribution](https://pypi.org/project/onnxruntime-directml/1.24.3/#files). It extracts `onnxruntime.dll`, `DirectML.dll`, `onnxruntime_providers_shared.dll`, and the two upstream licence files from that exact archive. MSI and NSIS place the DLLs beside the executable and the notices in `licenses/`. The packaged app does not install Python or a Python extension. This DirectML build imports the Microsoft Visual C++ x64 runtime; account for that prerequisite on a clean Windows installation. If DirectML session setup fails, the separator tries a CPU session and reports CPU as the backend.
- **Android arm64:** After `tauri android init`, the stager downloads Microsoft’s versioned AAR from Maven Central. It checks both the archive and extracted library against the [checked-in verification report](../reports/android-onnx-runtime-1.24.3.json) before staging. A mismatch stops the job before it builds an APK. The signing workflow checks the packaged arm64 library’s ELF load alignment and verifies the unmodified notices in the signed APK.
- **Development:** No libraries are downloaded by normal checks. If running a native development build, set `ORT_DYLIB_PATH` to the absolute path to a compatible local library, or stage the Android library in the generated app. On Windows without an override the app uses the DLL beside the executable; Android uses the app's native-library search path. If the library cannot be opened, model operations return an error instead of panicking in `ort`'s implicit load path.

## Android C++ dependency

The linked ARM64 application depends on `libc++_shared.so`; it is not treated as an Android system library. The Linux packaging runner stages it from the same NDK r28c sysroot used to compile the app, alongside the NDK's `NOTICE` and `NOTICE.toolchain` files. The no-APK Android native check exercises staging with the real SDK. The final signed APK check requires exactly one ARM64 copy of the app library, ONNX Runtime and the C++ runtime, checks every packaged native library for 16 KiB-compatible ELF load segments, and compares the C++ runtime's GNU build ID with the NDK copy. The build ID comparison tolerates Gradle symbol stripping. The Android device linker, Kotlin/Gradle package and audio output still need their own verification.

## Check the real provider archives without making an APK

The **Native runtime preflight** workflow (`runtime-preflight.yml`), run manually or on a pull request that changes runtime staging, verifies the Windows archive and fetches the Android AAR from Maven Central. It inspects the arm64 library and produces `android-onnx-runtime.json` with the observed SHA-256 and byte sizes of the archive and library, a list of any licence or notice entries, the exact Android Maven POM’s licence declarations, the staged notice hashes and the ELF’s dynamic dependencies. Maven declarations and ELF dependencies do not enumerate all statically linked third-party code. It does not use signing keys, create an Android project, or compile the app. The runner compares its new observation to the checked-in pin. The [initial GitHub run](https://github.com/AndrexTheDev/ChampionVibe/actions/runs/44945845723) verified the Maven source and supplied the recorded digests. To inspect a deliberate update before changing its pin, run the inspection command without `--check-pin` on a Maven-capable host; then review the result before changing the checked-in report.

## Android runtime notices

The pinned AAR did not include separate notice files. `legal/onnxruntime/1.24.3/` carries Microsoft's exact-release `LICENSE` and `ThirdPartyNotices.txt`, extracted byte for byte from its [ONNX Runtime 1.24.3 CPU distribution](https://pypi.org/project/onnxruntime/1.24.3/#files) (`onnxruntime-1.24.3-cp312-cp312-win_amd64.whl`, SHA-256 `44ea708c34965439170d811267c51281d3897ecfc4aa0087fa25d4a4c3eb2e4a`). Only the two texts, not the Windows binaries, go in the Android app under `assets/championvibe-licenses/onnxruntime/`. They establish the upstream notices baseline, not that an Android-specific dependency audit is complete.

The [Android-specific evidence run](https://github.com/AndrexTheDev/ChampionVibe/actions/runs/44948793680) confirmed that the 1.24.3 Maven descriptor declares MIT, the pinned ARM64 library has only Android platform dependencies (`libdl.so`, `liblog.so`, `libandroid.so`, `libm.so`, `libc.so`), and the two staged notices match the checked-in hashes. The AAR still has no standalone notice entries. The app itself, separately from ONNX Runtime, needs the NDK C++ library described above. This evidence does not resolve the notices for all Android Gradle dependencies or establish redistribution clearance.

## Verification before distribution

- Run the offline staging tests with `python3 tests/onnx_runtime_test.py`; they check archive selection, architecture and layout, not real inference.
- On the final Windows 10 and physical Android installs, confirm the native library loads with no developer override. Import a track with the cleared Spleeter model and verify both stems play. On Windows test CPU and DirectML (where available); on Android also check OS compatibility and native library alignment on a 16 KB page-size device where applicable.
- Verify the Windows installer carries the vendor notice files and review any binary-specific redistribution terms before public distribution. For Android, verify the real AAR and review which notices must ship. Staging checks archive bytes and layout; it does not establish legal clearance or prove native dependencies load.
