# Native ONNX Runtime in release builds

ChampionVibe uses ONNX Runtime **1.24.3** for native model validation and stem separation. `ort` rc.12 requests API 24. Kokoro speech still uses a separate WebAssembly runtime in the WebView.

- **Windows x64:** `scripts/stage-onnx-runtime.py windows` verifies the SHA-256 of Microsoft’s [ONNX Runtime DirectML 1.24.3 distribution](https://pypi.org/project/onnxruntime-directml/1.24.3/#files). It extracts `onnxruntime.dll`, `DirectML.dll`, `onnxruntime_providers_shared.dll`, and the two upstream licence files from that exact archive. MSI and NSIS place the DLLs beside the executable and the notices in `licenses/`. The packaged app does not install Python or a Python extension. This DirectML build imports the Microsoft Visual C++ x64 runtime; account for that prerequisite on a clean Windows installation. If DirectML session setup fails, the separator tries a CPU session and reports CPU as the backend.
- **Android arm64:** After `tauri android init`, the stager downloads Microsoft’s versioned AAR from Maven Central. It validates the archive against the reviewed `ANDROID_ONNX_RUNTIME_SHA256` value supplied via `--sha256` before copying `jni/arm64-v8a/libonnxruntime.so` to Gradle’s `jniLibs`. The value is required by the release job, and a malformed or mismatched digest stops it before building the APK. The final workflow checks the signed APK for the arm64 library.
- **Development:** No libraries are downloaded by normal checks. If running a native development build, set `ORT_DYLIB_PATH` to the absolute path to a compatible local library, or stage the Android library in the generated app. On Windows without an override the app uses the DLL beside the executable; Android uses the app's native-library search path. If the library cannot be opened, model operations return an error instead of panicking in `ort`'s implicit load path.

## Check the real provider archives without making an APK

The **Native runtime preflight** workflow (`runtime-preflight.yml`), run manually or on a pull request that changes runtime staging, verifies the Windows archive and fetches the Android AAR from Maven Central. It inspects the arm64 library and produces `android-onnx-runtime.json` with the observed SHA-256 and byte sizes of the archive and library, and a list of any licence or notice entries. It does not use signing keys, create an Android project, or compile the app. A recorded digest is an observation, not an independent pin; review the source and digest before setting the public `ANDROID_ONNX_RUNTIME_SHA256` variable in GitHub’s `android-release` environment. No Android archive digest has been committed or configured by this change.

## Verification before distribution

- Run the offline staging tests with `python3 tests/onnx_runtime_test.py`; they check archive selection, architecture and layout, not real inference.
- On the final Windows 10 and physical Android installs, confirm the native library loads with no developer override. Import a track with the cleared Spleeter model and verify both stems play. On Windows test CPU and DirectML (where available); on Android also check OS compatibility and native library alignment on a 16 KB page-size device where applicable.
- Verify the Windows installer carries the vendor notice files and review any binary-specific redistribution terms before public distribution. For Android, verify the real AAR and review which notices must ship. Staging checks archive bytes and layout; it does not establish legal clearance or prove native dependencies load.
